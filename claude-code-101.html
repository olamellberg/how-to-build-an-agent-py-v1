Claude Code 101

En praktisk handbok för att leverera riktiga ändringar säkert med Claude Code A practical playbook for shipping real changes safely with Claude Code

TänkThink CLAUDE.md KontextContext Prompting MCP TL;DR

Den här guiden är en Claude Code-specifik "101" för systemutvecklare. Målet är inte teori — det är en uppsättning repeterbara arbetsflöden som producerar små diffar, snabb feedback och färre regressioner. This guide is a Claude Code–specific "101" for system developers. The goal is not theory—it's a set of repeatable workflows that produce small diffs, fast feedback, and fewer regressions.

Officiell Claude Code-dokumentation: https://code.claude.com/docs/ Official Claude Code docs: https://code.claude.com/docs/

Tänk först (använd Plan Mode, exekvera sedan) Think first (use Plan Mode, then execute)

Claude Code fungerar bäst när första steget är att strukturera problemet, inte att skriva instruktioner. Claude Code works best when the first step is structuring the problem, not typing instructions.

Varför detta spelar roll Why this matters

Om förfrågan är bred kommer Claude fylla i luckor med "rimliga standardvärden". I ingenjörsarbete blir dessa ofta: If the request is broad, Claude will fill in gaps with "reasonable defaults." In engineering work, those defaults often become:

  • onödiga abstraktioner unnecessary abstractions
  • för många filer too many files
  • dolda beteendeförändringar hidden behavior changes
Motivering: tvetydighet ökar lösningsrymden, och modellen kommer utforska den. Rationale: ambiguity increases solution space, and the model will explore it.

Vad du ska göra What to do

  1. Skriv måltillståndet (acceptanskriterier) innan du ber om kod.
    Motivering: Claude är starkast när den optimerar för ett explicit "klart", inte ett underförstått.     Write the target state (acceptance criteria) before asking for code.
    Rationale: Claude is strongest when optimizing for an explicit "done," not an implied one.
  2. Använd Plan Mode för allt som påverkar arkitektur, data, auth eller gränssnitt.
    I Claude Code, gå in i Plan Mode (vanligtvis Shift+Tab två gånger beroende på setup).
    Motivering: planering tvingar fram explicita gränser och minskar överraskande ändringar.     Use Plan Mode for anything that affects architecture, data, auth, or interfaces.
    In Claude Code, enter Plan Mode (commonly Shift+Tab twice depending on setup).
    Rationale: planning forces explicit boundaries and reduces surprise edits.
  3. Be om alternativ och avvägningar först, välj sedan.
    Exempelprompt: "Lista 2–3 möjliga designs, peka ut risker, och rekommendera en. Skriv ingen kod ännu."
    Motivering: den snabbaste vägen är ofta att välja rätt approach tidigt.     Ask for options and tradeoffs first, then choose.
    Example prompt: "List 2–3 viable designs, call out risks, and recommend one. Do not write code yet."
    Rationale: the fastest path is often picking the right approach early.

Ersätt vagt med specifikt Replace vague with specific

Dåligt:Bad:

  • "Bygg ett auth-system." "Build an auth system."

Bra:Good:

  • "Lägg till email/lösenord-auth med befintliga User-modellen; lagra sessioner i Redis med 24h utgång; skydda routes under /api/protected; inga nya beroenden; lägg till integrationstester." "Add email/password auth using the existing User model; store sessions in Redis with 24h expiry; protect routes under /api/protected; no new dependencies; add integration tests."
Motivering: specificitet förhindrar övergrepp och skapar verifierbar output. Rationale: specificity prevents overreach and creates a verifiable output.

Arkitektur är inte valfritt (det är hur du begränsar modellen) Architecture isn't optional (it's how you constrain the model)

Claude kan generera fungerande kod som bryter mot ditt systems invarianter. Lösningen är inte "bättre kodgenerering". Lösningen är arkitekturbegränsningar i förväg. Claude can generate working code that violates your system's invariants. The fix is not "better code generation." The fix is architectural constraints up front.

Vad du ska inkludera i din planförfrågan What to include in your plan request

  • Gränser: vilka moduler som kan/inte kan röra varandra Boundaries: what modules can/can't touch each other
  • Invarianter: vad som måste förbli sant Invariants: what must remain true
  • Icke-mål: vad som inte får ändras Non-goals: what must not change
  • Validering: kommandon som bevisar att det fungerar Validation: commands that prove it works
Motivering: begränsningar fungerar som skyddsräcken; utan dem uppfinner Claude struktur. Rationale: constraints act like guardrails; without them, Claude invents structure.

CLAUDE.md: din fil med högst hävstång CLAUDE.md: your highest-leverage file

CLAUDE.md är en Markdown-fil som Claude Code läser vid sessionens start. Den fungerar som beständiga repo-specifika instruktioner. CLAUDE.md is a Markdown file Claude Code reads at the start of a session. It functions as persistent repo-specific instruction.

Varför det spelar roll Why it matters

Det förvandlar upprepade korrigeringar till ett stabilt kontrakt: It turns repeated corrections into a stable contract:

  • "använd detta testkommando" "use this test command"
  • "formatera inte om orelaterade filer" "don't reformat unrelated files"
  • "undvik nya abstraktioner" "avoid new abstractions"
  • "följ dessa konventioner" "follow these conventions"
Motivering: beständig vägledning minskar promptlängd och ökar konsekvens mellan sessioner. Rationale: durable guidance reduces prompt length and increases consistency across sessions.

Hur du skriver en bra CLAUDE.md How to write a good CLAUDE.md

  • Håll den kort. Om du inkluderar för mycket kommer Claude ignorera instruktioner oförutsägbart.
    Motivering: instruktionsöverbelastning skapar prioritetskonflikter.     Keep it short. If you include too much, Claude will ignore instructions unpredictably.
    Rationale: instruction overload creates priority conflicts.
  • Gör den repo-specifik. Undvik generiska förklaringar ("vad komponenter är"). Inkludera de konstiga, lokala reglerna.
    Motivering: Claude känner redan till generella mönster; den behöver dina specifika.     Make it repo-specific. Avoid generic explanations ("what components are"). Include the weird, local rules.
    Rationale: Claude already knows general patterns; it needs your specific ones.
  • Förklara "varför", inte bara "vad". "Använd TypeScript strict mode eftersom implicit any orsakade produktionsbuggar."
    Motivering: "varför" hjälper Claude göra bättre bedömningar i kantfall.     Explain "why," not only "what." "Use TypeScript strict mode because implicit any caused production bugs."
    Rationale: the "why" helps Claude make better judgment calls in edge cases.
  • Uppdatera den kontinuerligt. Varje gång du korrigerar samma misstag två gånger, lägg till en instruktion.
    Motivering: detta ackumuleras — varje fix förhindrar framtida omarbete.     Update it continuously. Any time you correct the same mistake twice, add an instruction.
    Rationale: this compounds—each fix prevents future rework.

En praktisk CLAUDE.md-starter (kopiera/klistra) A practical CLAUDE.md starter (copy/paste) 

# CLAUDE.md (project instructions)

## Goals
- Produce minimal, reviewable diffs.
- Prefer existing patterns in this repo.

## Non-goals
- Do not introduce new dependencies without explicit request.
- Do not reformat unrelated files.
- Do not create new abstractions unless asked.

## Commands (run after edits)
- Format: <cmd>
- Lint: <cmd>
- Typecheck: <cmd>
- Tests: <cmd>

## Architecture constraints
- Keep domain logic out of HTTP handlers.
- No DB access in middleware unless explicitly required.
- Keep public API backwards compatible by default.

## Working style
- Start with a 3–7 step plan.
- After each step: summarize diff + commands run + remaining risks.
- If uncertain: stop and ask for a decision.

"Ultrathink"-läge (kvalitetsfokuserat mindset) "Ultrathink" mode (quality-first mindset)

Vissa team använder en kort, högvärdig "kvalitetsribba" i sin projektvägledning för att få Claude att prioritera genomtänkt planering, noggrann läsning och minimal komplexitet. Detta kan ligga i CLAUDE.md (eller i en separat QUALITY.md som refereras från CLAUDE.md) så länge det förblir koncist. Some teams use a short, high-signal "quality bar" in their project guidance to bias Claude toward deliberate planning, careful reading, and minimal complexity. This can live in CLAUDE.md (or in a separate QUALITY.md referenced from CLAUDE.md) as long as it stays concise.

Principer att koda in (och varför de hjälper) Principles to encode (and why they help)

  • Tänk annorlunda: ifrågasätt antaganden och överväg enklare arkitekturer före implementation.
    Motivering: den första fungerande lösningen är ofta inte den bästa för långlivade system.     Think different: question assumptions and consider simpler architectures before implementation.
    Rationale: the first working solution is often not the best fit for long-lived systems.
  • Var besatt av detaljer: läs befintlig kod som en specifikation — följ etablerade mönster och namngivning.
    Motivering: konsekvens minskar integrationsbuggar och håller diffar granskningsbara.     Obsess over details: read existing code like a specification—follow established patterns and naming.
    Rationale: consistency reduces integration bugs and keeps diffs reviewable.
  • Planera som en designer: skriv en kort plan som gör gränssnitt och invarianter explicita innan du redigerar filer.
    Motivering: explicita gränser förhindrar trovärdig-men-felaktig kodgenerering.     Plan like a designer: write a short plan that makes interfaces and invariants explicit before editing files.
    Rationale: explicit boundaries prevent plausible-but-wrong code generation.
  • Hantverk, inte spretighet: håll funktioner och abstraktioner minimala; undvik att introducera nya lager om det inte efterfrågas.
    Motivering: onödig inriktning ökar underhållskostnad och döljer defekter.     Craft, don't sprawl: keep functions and abstractions minimal; avoid introducing new layers unless requested.
    Rationale: unnecessary indirection increases maintenance cost and hides defects.
  • Iterera obevekligt: validera efter varje steg (tester, skärmdumpar, jämförelser) och förfina tills det är korrekt och rent.
    Motivering: frekvent feedback fångar regressioner tidigt och förkortar vägen till "klart".     Iterate relentlessly: validate after each step (tests, screenshots, comparisons) and refine until it's correct and clean.
    Rationale: frequent feedback catches regressions early and shortens the path to "done."
  • Förenkla hänsynslöst: ta bort komplexitet när den inte ger mätbart värde.
    Motivering: enklare system misslyckas på färre sätt och är lättare att drifta.     Simplify ruthlessly: remove complexity when it doesn't buy measurable value.
    Rationale: simpler systems fail in fewer ways and are easier to operate.

Kontextfönster degraderas tidigare än du tror Context windows degrade earlier than you think

Även med stora kontextfönster tenderar kvaliteten att sjunka innan du "fyller ribban". Symtom inkluderar: Even with large context windows, quality tends to drop before you "fill the bar." Symptoms include:

  • upprepar samma misstag repeating the same mistake
  • tappar bort begränsningar losing track of constraints
  • hallucinerar struktur du aldrig begärde hallucinating structure you never requested
Motivering: mer kontext ökar konkurrensen om uppmärksamhet; viktiga detaljer förlorar betydelse. Rationale: more context increases competition for attention; important details lose salience.

Praktiska kontexthanteringstekniker Practical context management techniques

  1. En konversation per uppgift
    Använd inte samma session för att bygga auth och refaktorera databaslager.
    Motivering: orelaterad kontext läcker och skapar felaktiga antaganden.     One conversation per task
    Don't use the same session to build auth and refactor database layers.
    Rationale: unrelated context bleeds and creates wrong assumptions.
  2. Använd externa minnesfiler
    Låt Claude skriva till SCRATCHPAD.md, plan.md, eller devdocs/progress.md.
    Motivering: filer består mellan sessioner och förankrar "sanningen" i repot.     Use external memory files
    Have Claude write to SCRATCHPAD.md, plan.md, or devdocs/progress.md.
    Rationale: files persist across sessions and anchor the "truth" in the repo.
  3. Kopiera-klistra reset-arbetsflöde (snabbt och effektivt)
    När saker blir uppsvällda:
    – kör /compact för att få en sammanfattning
    – kör /clear för att nollställa kontext
    – klistra tillbaka endast den kritiska planen + begränsningar + aktuella fel
    Motivering: en liten, ren kontext överträffar ofta en stor, degraderad.     Copy–paste reset workflow (fast and effective)
    When things get bloated:
    – run /compact to get a summary
    – run /clear to reset context
    – paste back only the critical plan + constraints + current errors
    Rationale: a small, clean context often outperforms a large, degraded one.
  4. Vet när du ska rensa
    Om sessionen är förvirrad, nollställ tidigt. CLAUDE.md ger fortfarande grundläggande vägledning.
    Motivering: att felsöka en förvirrad kontext är långsammare än att starta om med ett rent briefing.     Know when to clear
    If the session is confused, reset early. CLAUDE.md still provides baseline guidance.
    Rationale: debugging a confused context is slower than restarting with a clean brief.
