Vibe Engineering 101

En praktisk guide för systemutvecklare som vill komma igång med agentbaserad utveckling A practical guide for system developers getting started with agentic development

Agentbaserad utveckling handlar mindre om "AI som skriver kod" och mer om att designa en pålitlig loop: en modell föreslår ändringar, verktyg validerar dem, och återkoppling driver nästa iteration. Den här artikeln är en fältguide för att bygga den loopen så att den producerar användbar mjukvara — konsekvent. Agentic development is less about "AI that writes code" and more about designing a reliable loop: a model proposes changes, tools validate them, and feedback drives the next iteration. This article is a field guide for building that loop so it produces useful software — consistently.

Målet här är inte att romantisera "vibe coding", utan att göra det operationellt: tydliga begränsningar, snabb feedback och repeterbara resultat. The goal here is not to romanticize "vibe coding," but to make it operational: clear constraints, fast feedback, and repeatable outcomes.

1) Vad en agent faktiskt är 1) What an "agent" actually is

En användbar arbetsdefinition är: A useful working definition is:

En agent kör verktyg i en loop för att uppnå ett mål. An agent runs tools in a loop to achieve a goal.

Ur ett ingenjörsperspektiv är det medvetet oglamoröst. Systemet är typiskt: From an engineering perspective, that's intentionally unglamorous. The system is typically:

  1. Ange ett mål + begränsningar Provide a goal + constraints
  2. Modellen föreslår åtgärder (redigera filer, köra kommandon, inspektera utdata) Model proposes actions (edit files, run commands, inspect outputs)
  3. Verktyg körs (tester, linters, byggen, sökning, exekvering) Tools run (tests, linters, builds, search, execution)
  4. Resultaten går tillbaka in i loopen Results go back into the loop
  5. Upprepa tills acceptanskriterierna är uppfyllda Repeat until the acceptance criteria are satisfied
Nyckelpunkt Key Point

Denna enkelhet är goda nyheter: det betyder att agentbaserade system går att konstruera och förbättra. Du kan förbättra dem genom att förbättra loopen, inte genom att behandla modellen som magi. This simplicity is good news: it means agentic systems are engineerable. You can improve them by improving the loop, not by treating the model as magic.

2) Ditt kontextfönster är ditt "RAM" 2) Your context window is your "RAM"

LLM:er "minns" inte ditt repo — i varje ögonblick arbetar de på de tokens du har tillhandahållit (plus vad dina verktyg injicerar). Praktiskt: LLMs don't "remember" your repository — at any moment, they operate on the tokens you've provided (plus whatever your tooling injects). Practically:

  • Allt som spelar roll måste finnas i kontexten (eller vara pålitligt hämtbart via verktyg). Everything that matters must be in context (or reliably retrievable via tools).
  • Mer kontext är inte alltid bättre. Överfulla kontexter ökar förvirring, felaktig verktygsanvändning och subtila fel. More context is not always better. Overstuffed contexts increase confusion, tool misuse, and subtle errors.
  • Du behöver hantera vad som kommer in i loopen. You need to manage what enters the loop.

Praktiska tumregler Practical rules of thumb

  • Undvik att låta verktyg dumpa stora mängder loggar, diffar eller hela repon i prompten. Avoid letting tools dump huge blobs of logs, diffs, or entire repos into the prompt.
  • Håll återkopplingen minimal och handlingsbar (mer om detta i rigg-avsnittet). Keep feedback minimal and actionable (more on this in the harness section).
  • Om din agent/verktyg auto-injicerar kontext, lär dig vad det inkluderar och hur du ställer in det. If your agent/tooling auto-injects context, learn what it includes and how to tune it.
Mental modell: Behandla kontextfönstret som ont om minne i äldre system. Om du låter det fyllas med brusiga loggar och redundant information, försämras prestandan på samma sätt som en begränsad maskin när den svälter på resurser. Mental model: Treat the context window like scarce memory in older systems. If you let it fill with noisy logs and redundant information, you'll degrade performance the same way a constrained machine does when starved of resources.

3) Den stora frikopplingen: skriva kod vs systemdesign 3) The great decoupling: typing code vs engineering systems

Agentbaserad utveckling förstärker ett skifte som många utvecklare redan upplever med senioritet: Agentic development amplifies a shift many developers already experience with seniority:

  • Programmering (skriva kod) blir billigare. Programming (typing code) becomes cheaper.
  • Engineering (design, begränsningar, testning, avvägningar) blir mer värdefullt. Engineering (design, constraints, testing, tradeoffs) becomes more valuable.

Modeller är ofta mycket starka på: Models are often very strong at:

  • syntax och boilerplate syntax and boilerplate
  • översätta avsikt till implementation translating intent into implementation
  • generera variationer snabbt generating variations quickly
  • arbeta i okända ekosystem (med vägledning) working across unfamiliar ecosystems (with guidance)

De är fortfarande svaga eller opålitliga på: They're still weak or unreliable at:

  • förstå din affärskontext som standard understanding your business context by default
  • göra produktavvägningar utan tydliga prioriteringar making product tradeoffs without clear priorities
  • gissa icke-uppenbara systembegränsningar guessing non-obvious system constraints
  • upprätthålla koherens över långa, röriga historiker maintaining coherence over long, messy histories
Rollskifte Role Shift

Rollen förändras: du spenderar mer tid på specifikationer, acceptanskriterier, tester och arkitektur — och mindre tid på tangenttryckningar. The role changes: you spend more time on specs, acceptance criteria, tests, and architecture — and less time on keystrokes.

4) Du är nu Tech Lead + QA Lead 4) You are now Tech Lead + QA Lead

En produktiv inramning är: A productive framing is:

  • Du definierar "klart". You define "done."
  • Du designar feedback-loopen. You design the feedback loop.
  • Du granskar utfall, inte varje rad. You review outcomes, not every line.

Modeller beter sig som extremt snabba medarbetare utan långtidsminne. De kan röra sig snabbt, men de behöver: Models behave like extremely fast collaborators with no long-term memory. They can move quickly, but they need:

  • tydliga begränsningar clear constraints
  • skarpa definitioner av framgång crisp definitions of success
  • deterministisk feedback (tester, lint, bygge) deterministic feedback (tests, lint, build)
  • skyddsräcken mot drift guardrails against drifting
Kärnkompetens: Bygg "modell-CI" in i ditt arbetsflöde. Core skill: Build "model CI" into your workflow.

5) Sluta brottas med modellen — bygg en bättre rigg 5) Stop fighting the model — build a better harness

Ett vanligt felläge är att behandla modellen som en junior utvecklare du måste mikromanagera i realtid. Det skapar en mänsklig flaskhals och minskar genomströmningen. A common failure mode is treating the model like a junior developer you must micromanage in real time. That creates a human bottleneck and reduces throughput.

Istället för att manuellt fixa formatering, namn eller små stilproblem: Instead of manually fixing formatting, names, or tiny style issues:

  • koda regler i verktyg (formatter/linter) encode rules into tooling (formatter/linter)
  • låt agenten köra verktygen let the agent run the tooling
  • använd fel som feedback-signaler use failures as feedback signals

När agenten går åt fel håll, anta att något av detta är sant: When the agent goes in the wrong direction, assume one of these is true:

  1. Planen var underspecificerad. The plan was under-specified.
  2. Acceptanskriterierna var vaga. The acceptance criteria were vague.
  3. Feedback-loopen är svag eller brusig. The feedback loop is weak or noisy.
Lösningen The Fix

Lösningen är sällan "titta hårdare". Det är vanligtvis: förbättra specen, skärp testerna, minska brus i output, försök om rent. The fix is rarely "watch harder." It's usually: improve the spec, tighten the tests, reduce noise in outputs, retry cleanly.

6) Projektupplägg är allt 6) Project setup is everything

Den bästa tidsinvesteringen du kan göra är ett repo som en agent kan arbeta i utan förvirring. The best time investment you can make is a repo that an agent can operate without confusion.

Hårt krav: ett kommando för att validera Hard requirement: one command to validate

Ditt projekt ska bygga, testa och linta med ett enda kommando. Your project should build, test, and lint with a single command.

Exempel: Examples: 

make check
./scripts/ci.sh
npm test
cargo test && cargo fmt --check && cargo clippy

Om validering kräver stamkunskap ("exportera denna variabel", "kör detta i den mappen", "installera detta systemberoende manuellt"), kommer din loop att slösa kontext och tid på att återupptäcka det — om och om igen. If validation requires tribal knowledge ("export this var," "run this in that directory," "install this system dependency manually"), your loop will waste context and time re-discovering it — over and over.

Minimera och forma output Minimize and shape output

Allt som skrivs ut av dina verktyg blir del av agentens arbetsminne. Behandla loggar som ett gränssnitt till en automatiserad medarbetare: Everything printed by your tools becomes part of the agent's working memory. Treat logs as an interface to an automated collaborator:

  • Föredra koncisa sammanfattningar vid framgång — "✅ 1000 tester godkända" slår 1000 rader av "ok" Prefer concise summaries on success — "✅ 1000 tests passed" beats 1000 lines of "ok"
  • Föredra fokuserade fel — visa det felande påståendet, relevant diff, minimal stacktrace Prefer focused failures — show the failing assertion, relevant diff, minimal stack trace
  • Undvik att dumpa tusentals rader av kompilatorspam om du kan kollapsa det Avoid dumping thousands of lines of compiler spew if you can collapse it
Detta är "context engineering" i praktiken: designa I/O så att modellen ser signal, inte brus. This is "context engineering" in practice: design the I/O so the model sees signal, not noise.

7) Lita på loopen, inte dina ögon 7) Trust the loop, not your eyes

Agentbaserade arbetsflöden skalar när du kan låta agenten köra utan konstant övervakning. Agentic workflows scale when you can let the agent run without constant supervision.

För att komma dit behöver du: To get there, you need:

  • deterministiska byggen deterministic builds
  • pålitliga tester reliable tests
  • linters/formatters linters/formatters
  • tydliga exit-koder clear exit codes
  • stabila skript stable scripts

En stark rigg gör det säkert att delegera: A strong harness makes it safe to delegate:

  • agenten ändrar kod the agent changes code
  • kör validering runs validation
  • läser felen reads the failures
  • itererar tills grönt iterates until green
  • presenterar en sammanfattning och den slutliga diffen presents a summary and the final diff
Din roll: Verifiering via kontrakt: "Uppfyller det specen och klarar checkarna?" Your role: Verification-by-contract: "Does it meet the spec and pass the checks?"

8) Designa för svarta lådor 8) Design for black boxes

Agentbaserad utveckling belönar modularitet. Agentic development rewards modularity.

Favorisera komponenter som är: Favor components that are:

  • små small
  • testbara isolerat testable in isolation
  • definierade av tydliga inputs/outputs defined by clear inputs/outputs
  • utbytbara utan att skriva om världen swappable without rewriting the world

Tänk "svarta lådor-moduler", inte nödvändigtvis microservices: Think "black box modules," not necessarily microservices:

  • ett CLI-verktyg med stabila flaggor a CLI tool with stable flags
  • ett bibliotek med ett smalt gränssnitt a library with a narrow interface
  • en tjänst med en strikt API-gräns a service with a strict API boundary
  • ett pipeline-steg med explicita artefakter a pipeline stage with explicit artifacts
Fördel Benefit

Detta minskar mängden kod modellen måste hålla koherent på en gång och gör refaktoreringar säkrare. This reduces the amount of code the model must keep coherent at once and makes refactors safer.

9) CLI före IDE (för agenter) 9) CLI over IDE (for agents)

IDE-integrationer kan vara bekväma, men CLI har strukturella fördelar för agentbaserat arbete: IDE integrations can be convenient, but the CLI has structural advantages for agentic work:

  • Upptäckbarhet: --help lär ut verktyg utan extra kontext Discoverability: --help teaches tools without extra context
  • Determinism: skript beter sig likadant i CI som lokalt Determinism: scripts behave the same in CI as locally
  • Transparens: stdout/stderr är ett explicit gränssnitt du kan justera Transparency: stdout/stderr is an explicit interface you can tune
  • Komponerbarhet: lätt att kedja steg till ett kommando Composability: easy to chain steps into one command

Ett bra CLI-först arbetsflöde gör det också lättare att köra flera agentsessioner parallellt, eftersom varje session kan arbeta genom skript snarare än UI-tillstånd. A good CLI-first workflow also makes it easier to run multiple agent sessions in parallel, since each session can operate through scripts rather than UI state.

10) TDD blir ovanligt effektivt med agenter 10) TDD becomes unusually effective with agents

Klassisk, strikt Test-Driven Development kan kännas dyrt för människor. Med agenter skiftar ekonomin eftersom tester blir en ratt: Classic, strict Test-Driven Development can feel expensive for humans. With agents, the economics shift because tests become a steering wheel:

  1. Skriv ett fallande test (eller en fallande check) Write a failing test (or a failing check)
  2. Låt agenten implementera ändringen Let the agent implement the change
  3. Iterera tills grönt Iterate until green

Detta fungerar särskilt bra när: This works especially well when:

  • krav är skarpa requirements are crisp
  • edge cases är testbara edge cases are testable
  • framgång är observerbar via assertions success is observable via assertions

Skydda mot "fusk" Guard against "cheating"

Agenter kan ibland tillfredsställa tester på ytliga sätt (mocka för mycket, hårdkoda, kringgå logik). Motåtgärder: Agents may sometimes satisfy tests in shallow ways (mocking too much, hardcoding, bypassing logic). Countermeasures:

  • lägg till property-baserade tester där lämpligt add property-based tests where appropriate
  • testa flera fall (inte bara "happy path") test multiple cases (not just "happy path")
  • verifiera integrationsbeteende, inte bara enhetsbeteende verify integration behavior, not only unit behavior
  • inkludera negativa tester och invarianter include negative tests and invariants

11) Golden master-testning för portar och refaktoreringar 11) Golden master testing for ports and refactors

När du migrerar system eller gör stora refaktoreringar kan golden master-testning vara extremt effektiv: When you're migrating systems or doing large refactors, golden master testing can be extremely effective:

  • instrumentera det gamla systemet för att avge deterministiska spår (beslut, nyckelstate, outputs) instrument the old system to emit deterministic traces (decisions, key state, outputs)
  • spara spåret som "golden"-filen save the trace as the "golden" file
  • implementera det nya systemet implement the new system
  • säkerställ att det matchar golden-spåret byte-för-byte (eller via en normaliserad komparator) ensure it matches the golden trace byte-for-byte (or via a normalized comparator)

Detta är kraftfullt för: This is powerful for:

  • språkmigreringar language migrations
  • parser/serializer-omskrivningar parser/serializer rewrites
  • algoritm-refaktoreringar algorithm refactors
  • "samma beteende, annan implementation"-projekt "same behavior, different implementation" projects
Tips

Om spår innehåller icke-deterministiska värden (tidsstämplar, pekare, slumpmässiga seed), normalisera dem. If traces contain nondeterministic values (timestamps, pointers, random seeds), normalize them.

12) Lägg tid på planering (och gör den återanvändbar) 12) Spend time on planning (and make it reusable)

Agenter drar nytta av planer som är: Agents benefit from plans that are:

  • indelade i steg staged
  • explicita om begränsningar explicit about constraints
  • explicita om "klart" explicit about "done"
  • nedskrivna i repot written down inside the repo

En bra plan svarar på: A good plan answers:

  • vad bygger vi? what are we building?
  • vad är icke-mål? what are the non-goals?
  • vad är gränssnitten? what are the interfaces?
  • vad är invarianterna? what are the invariants?
  • vilka tester bevisar korrekthet? what tests prove correctness?
  • i vilken ordning ska ändringar landa? what order should changes land?

Modeller är också användbara som planeringsassistenter: Models are also useful as planning assistants:

  • be om arkitekturalternativ ask for architectural alternatives
  • begär risklistor request risk lists
  • generera ett fasat implementationsförslag generate a phased implementation proposal
  • identifiera saknade acceptanskriterier identify missing acceptance criteria
Men planen måste till slut spegla dina begränsningar och prioriteringar. But the plan must ultimately reflect your constraints and priorities.

13) DevDocs: överlev kontextåterställningar 13) DevDocs: surviving context resets

Långa sessioner tappar lätt fokus. En praktisk teknik är att hålla lättvikts \"agent handoff\"-dokument i repot, t.ex.: Long sessions degrade. A practical technique is to keep lightweight "agent handoff" docs in the repo, e.g.: 

devdocs/
  plan.md
  progress.md
  decisions.md   (valfritt/optional)
  notes.md       (valfritt/optional)

Föreslaget innehåll: Suggested contents:

devdocs/plan.md

  • mål / icke-mål goals / non-goals
  • arkitekturskiss architecture sketch
  • faser phases
  • acceptanskriterier acceptance criteria
  • kommandon att köra commands to run

devdocs/progress.md

  • nuvarande tillstånd current state
  • vad är klart (checkboxar) what's done (checkboxes)
  • vad är nästa steg what's next
  • kända problem known issues
  • länkar till relevanta filer links to relevant files
När sessionen blir rörig When the session gets messy

Starta en ny session, peka agenten på devdocs/plan.md + devdocs/progress.md, fortsätt med rent blad. Start a fresh session, point the agent at devdocs/plan.md + devdocs/progress.md, continue with a clean slate.

Nyckelinsikt: Planer och begränsningar är beständiga; kod är utbytbar. Key mindset: Plans and constraints are durable; code is replaceable.

14) Ackumulering och slaskrisk 14) Accumulation and "slop" risk

En verklig oro i agentbaserad utveckling är långsiktig kodkvalitetsdrift: A real concern in agentic development is long-term code quality drift:

  • inkonsekventa mönster inconsistent patterns
  • övervuxna abstraktioner overgrown abstractions
  • duplicerad logik duplicated logic
  • oklara gränser unclear boundaries

Motåtgärder: Mitigations:

  • upprätthåll formatering och linting enforce formatting and linting
  • kräv tester för ändringar require tests for changes
  • underhåll en arkitektur/beslutslogg maintain an architecture/decisions log
  • refaktorera medvetet i faser refactor deliberately in phases
  • härleda moduler på nytt från en ren spec periodiskt (när motiverat) periodically "re-derive" modules from a clean spec (when warranted)
  • håll moduler små och utbytbara keep modules small and replaceable
Behandla agenten som en höggenomsättlig bidragsgivare: utan styrning ackumuleras entropi. Treat the agent like a high-throughput contributor: without governance, entropy accumulates.

15) Bortom kodning: där agenter glänser 15) Beyond coding: where agents shine

Agentloopar är ofta mest värdefulla för arbete som är: Agentic loops are often most valuable for work that is:

  • nödvändigt men inte intellektuellt centralt necessary but not intellectually central
  • starkt iterativt highly iterative
  • verktygsdrivet tool-driven
  • lätt att validera easy to validate

Exempel: Examples:

  • fixa CI-fel fixing CI failures
  • uppdatera byggskript updating build scripts
  • repohygien (lint, formatering, beroendeuppgraderingar) repository hygiene (lint, formatting, dependency upgrades)
  • utforska okända kodstigar researching unfamiliar codepaths
  • generera minimala reprofall generating minimal repros
  • skriva migreringsskript writing migration scripts
  • operativ felsökning (när säkert och kontrollerat) operational troubleshooting (when safe and controlled)
Gemensamt tema Common theme

Loopen har tydlig verktygsfeedback och begränsad risk. The loop has clear tooling feedback and bounded risk.

16) Sub-agenter och delegeringsmönster 16) Sub-agents and delegation patterns

Ett skalningsmönster är att separera: One scaling pattern is separating:

  • utforskning (läs kod, kartlägg flöden, identifiera filer) exploration (read code, map flows, identify files)
  • exekvering (applicera ändringar, kör checkar, förfina) execution (apply changes, run checks, refine)

Du kan modellera detta som: You can model this as:

  • en "scout"-agent som returnerar en kort rapport: var relevant logik finns, hur anropsgrafen ser ut, vad som ska ändras och varför a "scout" agent that returns a short report: where the relevant logic lives, what the call graph looks like, what to change and why
  • en "builder"-agent som implementerar och validerar a "builder" agent that implements and validates
  • ett "reviewer"-steg som sammanfattar diffar och risker a "reviewer" step that summarizes diffs and risks
Detta hjälper till att kontrollera kontexttillväxt och minskar thrash. This helps control context growth and reduces thrash.

17) En praktisk startchecklista 17) A practical starter checklist

Om du vill att agentbaserad utveckling ska kännas produktiv snabbt, börja här: If you want agentic development to feel productive quickly, start here:

Repo-rigg Repository harness

  • Ett kommando: bygge + test + lint Single command: build + test + lint
  • Tydliga skript i ./scripts eller Makefile Clear scripts in ./scripts or Makefile
  • Minimala loggar vid framgång, handlingsbara loggar vid fel Minimal logs on success, actionable logs on failure
  • Deterministiska testkörningar Deterministic test runs

Arbetsflöde Workflow

  • Skriv acceptanskriterier först Write acceptance criteria first
  • Lägg till tester före eller tillsammans med ändringar Add tests before or alongside changes
  • Håll ändringar små och komponerbara Keep changes small and composable
  • Föredra moduler med smala gränssnitt Prefer modules with narrow interfaces

Kontexthygien Context hygiene

  • Klistra inte in enorma loggar/diffar om det inte är nödvändigt Don't paste huge logs/diffs unless necessary
  • Ge riktade filsökvägar och mål Provide targeted file paths and goals
  • Använd devdocs/ för beständig plan/progress Use devdocs/ for durable plan/progress

Kvalitetskontroller Quality controls

  • Linter + formatter + CI-grind Linter + formatter + CI gate
  • Golden master-approach för riskfyllda migreringar Golden master approach for risky migrations
  • Periodiska refaktoreringsfaser för att minska drift Periodic refactor phases to reduce drift

Avslutning Closing

"Vibe Engineering" blir verkligt när du behandlar agenter som en del av ett system: en loop med verktyg, begränsningar och återkoppling. Om du investerar i riggen och gör "klart" maskin-kontrollerbart, kan du delegera säkrare, röra dig snabbare och lägga mer tid på de ingenjörsbeslut som faktiskt spelar roll. "Vibe Engineering" becomes real when you treat agents as part of a system: a loop with tools, constraints, and feedback. If you invest in the harness and make "done" machine-checkable, you can delegate more safely, move faster, and spend more time on the engineering decisions that actually matter.
